# LogHunter 技术设计

> 本地大日志（GB 级）快速排查工具的完整技术设计：架构、低内存高效率的核心算法、以及 20GB 级真实压力测试数据。文中所有性能数字均为本机实测，非估算。

## 1. 系统概览

LogHunter 是 Windows 免安装单文件桌面应用（约 12MB exe），面向「拿到一批本地日志文件快速定位问题」的排查场景。四个设计目标：

| 目标 | 含义 | 达成手段 |
|---|---|---|
| **GB 级秒级响应** | 20GB 日志：全览 0ms、时间过滤 ~0.5s、时间合并 ~0.7s | 内存元数据索引 + 零物化全览 |
| **低内存** | 索引 17B/行（约 155MB/GB 日志）；全览浏览零额外内存；结果条数按物理内存自适应 | 平行数组索引 + 内存治理三件套 |
| **纯本地零残留** | 日志不出机器、索引不落盘；zip 解压产物随清空/退出自动删除 | 全内存会话 + 临时目录生命周期 |
| **免安装单文件** | 双击即用，无部署无依赖 | Wails v2 打包（Go + WebView2） |

## 3. 核心数据结构

### 3.1 行索引 LineIndex——三个等长平行数组

```go
type LineIndex struct {
    offsets     []int64   // 每行首字节偏移        8B/行
    ts          []int64   // 每行时间戳(unixNano)   8B/行，0=无时间戳
    levels      []int8    // 级别枚举              1B/行
    levelCounts [6]int    // 建索引时顺带累计（全览 O(文件数) 直取）
    maxLineLen  int       // 同上
}
```

**合计 17B/行 ≈ 155MB/GB 日志**。这是「时间过滤毫秒级直查」的全部成本，也是整个系统内存账的本钱——不建全文索引，任意关键字/正则仍可全扫（见 4.1 的取舍）。

### 3.2 结果三态（v0.0.5）

```
             无条件+平铺                切「时间合并」
 ┌──────────┐ ────────► ┌──────────────┐ ────────► ┌─────────────────┐
 │ modeQuery │  重新查询  │modeBrowseVirtual│  物化+排序 │ modeBrowseMat   │
 │ 条件查询物化│ ◄──────── │ 全览零物化视图  │ ◄──────── │ 全览物化(上限内)  │
 └──────────┘           └──────────────┘  丢弃物化   └─────────────────┘
```

- `modeQuery`：带条件查询（或合并）物化的 `[]ResultRow`，受自适应上限约束；
- `modeBrowseVirtual`：**纯全览（无条件+平铺）不存任何结果数组**——Total=Σ行数、GetResults 按窗口从索引现翻译，永不截断、额外内存≈0；
- `modeBrowseMat`：全览切到时间合并时按需物化（上限内），切回平铺即丢弃。

## 4. 关键算法（低内存与高效率的支撑）

### 4.1 元数据索引而非全文索引

时间/级别条件走内存索引 O(n) 直查（n=行数，纯数组扫描，1.85 亿行约 1s 内）；任意正则走并行全扫（无索引路径）。**为什么不建全文索引**：全文索引内存是索引量的数倍且构建分钟级；排查场景 90% 的查询带时间/级别条件，用 17B/行覆盖它们、剩下 10% 交给全扫，是内存与速度的最优交点。

### 4.2 分块并行扫描

文件按 **16MB 块**切分、块边界对齐到换行（`chunkPlan`），多核并行处理（`parallelChunks`）；建索引各块提取行首元组、按块序合并。多文件加载再叠加**文件间 4 路并行**（完成序重排回拖入序）。

### 4.3 查询与结果构建分离 + 顺序读游标

查询期只收集命中偏移（`ResultRow.Preview` 留空），预览文本在前端窗口拉取时按需生成——百万级命中的宽查询不因文本构建拖慢。预览读取用 **seqReader 4MB 顺序游标**：窗口行按 offset 升序访问时缓冲复用，无随机 IO、无逐行 seek。

### 4.4 全览零物化（v0.0.5 核心）

无条件全览是最高频操作（拖入即全览）。旧设计把它当「条件全空的查询」物化 200 万条截断——既慢又截断。现设计：

- **Total = 各文件行数之和**（一个数字），永不截断；
- GetResults 窗口内：全局行号 → **行数前缀和二分**定位文件 → 从 `offsets/ts/levels` 平行数组直取行元组，Preview 照旧惰性读；
- 级别统计/最长行用**建索引时预计算**的每文件汇总，O(文件数) 即时返回。

**内存账**：全览视图额外内存 ≈ 0。10GB 日志全览与 1MB 文件全览的成本相同（都只是已付的索引）。

### 4.5 时间锚点继承（筛选与合并的统一语义）

无时间戳的行（异常堆栈/SQL 续行）向前继承同文件上一条非零时间戳作锚点：

- **时间筛选**（`filterCandidates`）：维护 `lastTS` 单遍扫描，锚点在范围内的无时间行保留——主行命中则其上下文不丢；
- **时间合并**（排序 key）：同一规则算 key，多节点时间线上堆栈块紧贴主行不被同刻他节点行插散。

### 4.6 时间合并排序：索引排序 + 置换环原地重排

多文件按锚点 key 稳定归并成单一时间线。两个实现要点（各对应一次实测教训）：

1. **排 int32 下标而非数据**：`sort.Stable` 的 Swap 是整结构体交换（64B/次），387 万行需 O(n·log n) 次交换；改为排 4 字节下标数组、比较函数读 `keys[order[x]]`，再用**置换环跟随** O(n) 原地应用（每行至多一次结构体交换），避免 1.28GB 级副本。
2. **锚点扫描分离「进度」与「锚点」双指针**：进度指针每行无条件推进；若只在遇到非零时间戳时推进，遇到连续数十万行无时间区（SQL dump 续行）会退化成每行重扫全零区间——实测内层扫描 782 亿次、46.5s 卡死，修复后 0.67s。

### 4.7 groupedRead：合并序下的防随机 IO

平铺序结果天然按文件聚簇，顺序读即最优；时间合并序打乱聚簇后窗口内同文件行散布。groupedRead 把窗口行按 **(FileID, Offset) 排序后分组**，每组开一个 seqReader 升序读——平铺序下该排序是稳定 no-op，两种模式共用一条路径。

### 4.8 内存治理三件套（+ 一个反例）

| 机制 | 说明 | 实测效果 |
|---|---|---|
| **结果上限内存自适应** | 物理内存×25%÷64B/条，clamp [200 万, 2000 万]；Windows `GlobalMemoryStatusEx` 查询 | 16GB 机器 ≈2000 万条（约 1.28GB 结果内存）封顶 |
| **索引建完逐块释放** | 块结果边合并边置空，消除「块+最终索引」双份并存 | 建索引过程峰值约减半 |
| **大结果替换后延迟归还** | 旧结果 >500 万且 >新结果 4 倍时，延迟 1s 异步 `debug.FreeOSMemory`（全局 STW 不计入紧邻查询） | 工作集 10.5GB→3.5GB 及时回落 |
| 反例：`debug.SetMemoryLimit` | 软上限让 GC 持续满负荷，20GB 正则全扫 7.8s→25s | 已移除并记录在此 |

### 4.9 流式导出

导出按 **5000 行/批** 读行→写盘→释放，全览与查询两模式统一；不再全量补全文本常驻内存，千万行导出不撑爆内存。

### 4.10 编码与 zip

- GBK/UTF-8 自动探测；**关键字按文件编码预转换成字节匹配**（`encodeKeyword`），GBK 文件不做逐行转码全扫；
- zip 按**内容**判定文本（前 16KB 含 NUL 跳过），轮转命名 `.log.101` 照收；GBK 文件名解码；Zip Slip 防护 + 8GB 解压上限；临时目录随移除/清空/退出删除（零残留）。

### 4.11 前端渲染

- **虚拟滚动 + 分段画布**：固定行高 30px，只渲染可见窗口 ±15 行；浏览器画布 ~33M px 上限，超过按约 99 万行/段切换（段末「点击继续」）；
- **槽位复用**（v0.0.5）：v-for 的 key 用段内槽位号而非全局行号——滚动滑窗从「每帧挂载/卸载行组件」变为纯文本 patch；
- 无高亮条件时跳过高亮组件实例化（纯文本插值）；结果缓存 shallowRef 去深代理；行级 CSS `contain: layout style` 渲染隔离；
- 无时间戳文件的置尾/跳过、截断上限等状态均在结果栏行内提示。

### 4.12 启动与自动更新

- **启动**：`StartHidden` 隐藏启动，前端就绪上报后 `WindowShow`（Go 侧 3s 兜底）——窗口「出现即就绪」消除空窗期；启动耗时埋点写 `data/startup.log`（关于弹窗可见），用于区分 Defender 扫描/WebView2 冷启等外部因素；
- **自动更新**：检查 GitHub Release 资产 → 确认浮层 → 下载（进度事件）→ **sha256 强制校验**（历史版本无校验文件时过渡跳过）→ 解压（条目名精确匹配）→ **rename 自替换**（运行中 exe 改名 `.old` 让位、新 exe 落位、失败回滚）→ 立即/稍后重启；新进程启动时退避清理 `.old`。

## 5. 并发与生命周期

- **双锁模型**：`opMu` 串行化长操作（加载/查询/合并切换，防互相干扰），`s.mu`（RWMutex）保护 entries/results/stats；锁序 opMu→mu 全局一致；
- **进度事件**：引擎以函数参数回调进度，绑定层转 Wails 事件；80ms 节流；
- **零残留链**：移除文件（清引用、zip 子目录无人引用即删）→ 一键清空（删临时根 + 强制归还内存）→ 退出 shutdown 同清空。

## 7. 已知边界与取舍

- **全扫受磁盘带宽**：关键字/正则无索引路径，20GB 约 10~13s（~2GB/s 有效吞吐，含杀毒过滤驱动损耗）——这是「元数据索引而非全文索引」架构的既定取舍，带时间/级别条件时先索引筛后扫、秒级返回；
- **超大日志「全览+时间合并」**：合并需物化排序，受自适应上限截断（平铺全览不受限）；
- **非 Windows 平台**：物理内存查询按 8GB 假设兜底（产物仅发布 Windows）；
- **级别过滤**只作用于有级别信息的行（与时间锚点继承不同，级别无法继承）；
- 未签名 exe 可能被杀毒实时扫描拖慢启动（README 提供排除项指引），启动埋点（`data/startup.log`）用于区分内因外因。
