## 目标（为什么做）
用户用真实日志包（ams_api，8GB+ 解压、zip 套 zip、SQL/ES 查询续行密集）逐项暴露问题：①解压超 8GB 被误拒；②SQL 续行占比过高致文件被误判「无时间列」；③轮转切断的多行条目续行脱离时间轴；④大数据量导出点击后无反馈、导出中再点查询卡死、原生 alert 与主题割裂。

## 范围（做了什么，清单）
- **解压上限自适应**：8GB 写死 → clamp(物理内存, 8GB 保底, 128GB 封顶)，大内存机器可加载超大合法日志包
- **格式探测锚点继承**：续行（SQL/堆栈/JSON dump）继承上一时间戳不拖低密度，密集续行日志正确识别时间列
- **开头无时间行锚点**：时间合并/筛选一致地让「文件开头无时间行」继承本文件首条时间戳（不跨文件），轮转切断续行归位
- **导出进度 + 可取消**：进度事件驱动琥珀进度条模态框；导出为终端操作（遮罩阻塞其他操作）；可取消（后端每批检查取消标志停笔、已写部分保留、锁释放）
- **自研弹框/toast 替换原生 alert**：导出模态框（进度/取消确认/结果三态）+ 瞬态 toast，配色字体全走 token

## 影响面
无接口破坏；外层 zip 提示/显示名行为不变；导出前端绑定新增 `CancelExport`（wailsjs 绑定随 app.go 同步入库）。格式探测密度语义变更：SQL/堆栈续行密集的文件从「判 plain」改为「判有时间格式」。
